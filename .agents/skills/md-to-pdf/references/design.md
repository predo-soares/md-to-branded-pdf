# Design system

The project default is a restrained Geist document system on white A4 paper. Every Template uses bundled Geist by default, including text in generated charts and diagrams. The plain-document Template uses 20 mm margins, 11 pt body text, dark ink, understated rules, and a quiet code background. Headings are distinct without decorative serif styling. Its executable defaults live in `assets/plain-document.css`.

Each Template owns its layout contract and CSS. The approved résumé remains visually isolated in `assets/templates/resume-ats.html`; do not apply these plain-document defaults to it. Edit content to fit a Template. Change layout rules only when the user explicitly asks to change the Template or this design guide.
The résumé uses its established hierarchy and Geist typography. Its content flows naturally onto one or two A4 pages; earlier experience no longer starts a page by rule. The renderer does not compress text to hold a page count, and more than two pages are rejected.

The PDF is rendered from saved HTML with WeasyPrint. Keep the generated HTML as the reviewable visual source, and check actual PDF pages before approving a layout.
For the file that owns each Template or component, see `template-editing.md`.

Global profile choices are limited to font, accent, and paper color. The initial font is bundled Geist; custom choices include system UI and supported local or downloaded fonts. Document-level choices override the profile only for that build. The résumé remains fixed to Geist and its approved design. The other Templates apply profile choices without weakening their layout contracts.
The proposal Template retains its existing Geist-based cover and numbered-section styling under default settings. A customized profile can change only its font, accent, and paper color; page geometry, section structure, and spacing stay under the proposal Template's control.
The cover-letter Template preserves its name, contact, date, recipient, subject, salutation, body, and closing hierarchy. It uses one A4 page with 18 mm top/bottom and 20 mm side margins. Custom profile choices may change font, accent, and paper without changing this layout.
The one-pager Template uses one A4 page with 20 mm margins, a prominent title, a central-message paragraph, and compact supporting sections. Its executable rules live in `assets/one-pager.css`. Metrics have no reserved space: include a table or list only when the source provides values. An overflow error calls for editorial content changes unless the user explicitly changes the Template or this guide.
The long-document Template uses A4 paper with 22 mm top and 20 mm side/bottom margins. Its executable rules live in `assets/long-document.css`. Chapters flow naturally; headings avoid orphaning, table headers repeat, rows resist splitting, and image/caption figures stay together where supported. The layout does not impose a fixed page count.
The portfolio Template uses A4 paper with the same 22 mm top and 20 mm side/bottom margins. `assets/portfolio.css` gives case titles a clear break from the prior case while keeping Context, Approach, and optional Outcome visually consistent. Figures and captions stay together where supported. The Template has no placeholder for missing outcomes.
The analytical-report Template uses A4 paper and the same 22 mm top and 20 mm side/bottom margins. `assets/report.css` defines the report's heading, table, and page-break rules. The required section order makes the argument inspectable; optional financial context has no reserved space. Long reports paginate naturally, and table rows and figures resist splitting where supported.
The changelog Template uses A4 paper with 20 mm margins. `assets/changelog.css` gives each release a ruled heading, distinct category labels, and readable entry spacing. Release and category headings avoid breaking from the following content. Links remain visible and annotated in the PDF; the Template does not reorder or summarize release entries.
The pitch-deck Template uses 320 × 180 mm PDF pages with no outer page margin and a fixed 18 mm vertical/24 mm horizontal slide inset. `assets/deck.css` defines cover, assertion, and closing layouts. Decks remain PDF documents; saved HTML is an intermediate review surface. One slide occupies exactly one page. If content exceeds that geometry, the builder reports overflow and the author edits content rather than changing type scale, spacing, or slide dimensions.
Comparison and metrics slides share the fixed 16:9 geometry. Comparison tables have criterion and two alternative columns; metrics tables pair labels with emphasized values. CSS keeps row order and type sizes fixed. Sparse slides keep the same sizing, while dense slides trigger overflow rather than automatic compression.
Generated charts share one structured JSON format across analytical reports and pitch decks. `scripts/md_to_pdf/visuals/charts.py` computes SVG geometry for bars, lines, donuts, and waterfalls and HTML metric displays from authored labels and numbers. Waterfalls use signed changes; donuts require a positive total. Chart typography and figure spacing are defined in the report and deck stylesheets; authors never edit SVG coordinates. The 12-item limit bounds label density without reducing type sizes.
Timelines, flowcharts, quadrants, layer stacks, and swimlanes use project-owned neutral and blue sans-serif styling in `scripts/md_to_pdf/visuals/diagrams.py`. Their composition ideas are adapted from Kami, with the full upstream MIT notice retained in `assets/diagrams/KAMI-MIT-NOTICE.txt`. Long documents and decks use their own figure spacing and page geometry. Labels and item counts are bounded; layout coordinates are generated from structured data. A person must review the adapted vocabulary before public release.
For one-page letters and briefs and one-page-per-slide decks, the renderer keeps each Template's type sizes, spacing, and page geometry fixed. On overflow it names the first block that crosses the page contract and leaves the HTML as a review surface. Automatic ellipses and fit-to-page scaling are not part of the rendering pipeline.
